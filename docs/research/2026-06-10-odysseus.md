# Odysseus — Pattern Extraction & Verdict (Task C1)

**Date:** 2026-06-10
**Repo:** `https://github.com/pewdiepie-archdaemon/odysseus` (live — NOT a dead link)
**Clone:** `/tmp/oss-research/odysseus` (`git clone --depth 1`, 1062 files, default branch `dev`, v1.0)
**What it is:** self-hosted local-first AI workspace built on opencode + llmfit + Tongyi DeepResearch + ChromaDB + fastembed. SQLAlchemy ORM + FastAPI-style `routes/` layer.

**Lens:** wu wei. A pattern earns INTEGRATE only if it solves a problem DQIII8 *measurably* has, at lower complexity than what we run today. Anything that adds a daemon, queue, or DB for an unmeasured problem is DISCARD by default.

## Pattern 1 — Scheduled tasks → **DISCARD**

**Odysseus source:** `src/task_scheduler.py` (2331 lines).

What it is: a full async daemon.
- `TaskScheduler._loop()` polls `_check_due_tasks()` on an adaptive sleep capped at ≤60s; dispatches via `asyncio.create_task(self._execute_task(...))`.
- `_run_semaphore = asyncio.Semaphore(1)`, `_concurrency_cap = 1` — strict serial execution, plus an `_executing` set guarded by `_executing_lock`.
- `compute_next_run(...)` supports cron (`croniter`), once / daily / weekly / monthly, and IANA timezones.
- SQLAlchemy tables: `ScheduledTask`, `TaskRun`, `CrewMember`, `Note`. `HOUSEKEEPING_DEFAULTS` seeds cron tasks.
- Crash recovery on `start()`: stale runs → `"aborted"`, overdue `next_run` advanced +60s, default-assistant dedupe. Plus `TaskDeferred`/`TaskNoop` and task chaining with cycle detection.

= **daemon + queue + DB**, the exact triad wu wei says to reject absent a measured need.

**DQIII8 today:** scheduling is already covered by `bin/director.py` (CLI director), `autonomous_loop.sh` (the `j loop` driver), and the Instincts fast-path. The VPS also has system `cron` and `tmux` for the one batch workload that needs wall-clock triggering (intl-reports runs, launched only from an external tmux per `DYNAMIC.md`). There is no logged backlog of "missed scheduled task" errors and no queue-contention problem — `Semaphore(1)` is just serial execution, which `autonomous_loop.sh` already is.

**Verdict: DISCARD.** Adopting `TaskScheduler` would introduce a long-lived asyncio daemon and four new SQLAlchemy tables to replace `cron` + `autonomous_loop.sh`, solving a problem we don't have. If a future need for cron-syntax triggers inside the Python process ever appears, the *only* transplantable idea is the `compute_next_run()` pure function (cron/once/daily/weekly/monthly + tz) — copy that ~one function, never the daemon. Not today.

## Pattern 2 — fastembed ONNX vector + keyword memory → **DISCARD**

**Odysseus source:** `src/memory_vector.py` (252), `src/embeddings.py` (255), `src/embedding_lanes.py` (390).
**DQIII8 comparison targets:** `bin/agents/hybrid_search.py`, `bin/agents/vector_store.py`.

### What Odysseus actually does
- `MemoryVectorStore` (collection `odysseus_memories`) is **vector-only over ChromaDB**. `search()` does `collection.query(query_embeddings=..., include=["distances"])` and converts cosine distance to similarity `1.0 - distance` (`memory_vector.py:153-159`). There is **no keyword / BM25 / FTS lane** in the memory path — the "vector+keyword" framing does not match the code. Retrieval is pure ANN.
- Multi-lane design (`embedding_lanes.py`): two parallel ChromaDB collections — `LANE_CUSTOM` (user's HTTP embedder) and `LANE_FASTEMBED` (zero-config ONNX fallback). Each lane is a *separate* collection because "ChromaDB fixes a collection's dimension on first insert" (`embedding_lanes.py:1-7`). `query_lanes()` queries each healthy lane and `dedupe_results()` merges by id — a fallback/redundancy mechanism, **not** rank fusion.
- `embeddings.py`: HTTP-first (`EmbeddingClient`, OpenAI `/v1/embeddings` format, default `all-minilm:l6-v2`) with a `_http_embed_down` process latch; falls back to `FastEmbedClient` (ONNX `fastembed`, default `sentence-transformers/all-MiniLM-L6-v2`, **~384-dim**).

### What DQIII8 already runs (strictly more capable)
- `hybrid_search.py`: **three** signals — vector (sqlite-vec KNN cosine), keyword (FTS5 `bm25`), graph (relations BFS) — merged with **Reciprocal Rank Fusion** (RRF, k=60; weights vector 1.0 / keyword 0.7 / graph 0.5). Never fails on one empty source.
- `vector_store.py`: sqlite-vec `vec0` virtual table `vec_knowledge`, `EMBEDDING_DIM = 1024` (**bge-m3**, migrated from nomic-embed-text 768-dim), `distance_metric=cosine`, similarity `1 − distance` (same formula as Odysseus). FTS5 `chunks_fts` synced inline. Everything lives in the single `database/dqiii8.db` — no second datastore.

### Why DISCARD
1. **Capability is backwards.** Odysseus memory = vector-only ANN. DQIII8 = vector + FTS5 keyword + graph + RRF. Adopting Odysseus's memory would be a downgrade.
2. **The keyword half doesn't exist** in Odysseus's memory layer — so there is nothing to integrate on the keyword side that DQIII8 doesn't already do better with FTS5 + RRF.
3. **fastembed's ONNX fallback is dimensionally incompatible.** It emits ~384-dim vectors; the DQIII8 store is fixed at **1024-dim bge-m3**. A 384-dim vector cannot be MATCHed against a `FLOAT[1024]` vec0 column. It offers no advantage over DQIII8's existing (also-mismatched) sentence-transformers `all-MiniLM-L12-v2` fallback, and would mean adopting **ChromaDB as a second vector DB** alongside sqlite-vec — a new datastore for zero capability gain. Textbook wu-wei DISCARD.

**One idea worth noting, not adopting now:** the `_http_embed_down` latch (`embeddings.py:201-241`) — cache "embedding endpoint is down" once so every subsequent RAG/memory probe skips the connect-timeout instead of re-paying ~3s. DQIII8's `vector_store._embed_query()` re-probes Ollama bge-m3 on every query and only falls back per-call. **This is the single transplantable micro-optimization** in the whole pattern: a process-level latch so a down Ollama doesn't cost a connect-timeout per query. It's a ~10-line change to one existing file, adds no daemon/queue/DB — file it as a *possible* latency fix, contingent on logs actually showing repeated embed-probe stalls. Until measured: leave it. The pattern as a whole stays **DISCARD**.

## Pattern 3 — VRAM-aware cookbook → **DISCARD**

**Odysseus source:** `services/hwfit/` (built on llmfit) — `fit.py` (675), `profiles.py` (229), `hardware.py`, `models.py`, `image_models.py`.
**DQIII8 comparison target:** `.claude/rules/03_tiering_and_routing.md`.

### What Odysseus does
A **local hardware fit-scorer**. `fit.py` carries a `GPU_BANDWIDTH` table (~80 GPUs: 5090→1792 GB/s, H200→4800, Apple M-series unified memory, etc.), estimates tok/s from memory bandwidth ÷ quantized model size with a partial-offload harmonic blend (`_estimate_speed`, calibrated against a measured RX 9060 XT). `profiles.py` turns detected VRAM/RAM into ready-to-launch llama.cpp profiles (Quality/Balanced/Speed) with concrete flags — `n_gpu_layers`, `n_cpu_moe` (how many MoE experts to offload to CPU so weights+KV fit the VRAM budget), KV-cache type (`q4_0`/`q8_0`/`f16`), context — walking a quant ladder `Q8_0 → … → Q2_K` until one fits. Pure/deterministic, no benchmarking.

This answers: *"Given THIS GPU, which quant of which GGUF fits in VRAM and how fast will it run?"*

### What DQIII8's ladder is
`.claude/rules/03_tiering_and_routing.md` is a **cost-first API-routing ladder**: C (Ollama qwen2.5-coder:7b, $0) → B (Groq llama-3.3-70b, $0) → B+ (GitHub deepseek-v3/codestral, $0) → A (Sonnet ~$0.03) → S (Opus ~$0.20). Start at C, escalate only on explicit task-type match or tier failure; goal ≥70% ops on cheap tiers. Routing = Instincts fast-path (confidence>0.7) → Groq LLM classification → keyword fallback.

This answers a **different question**: *"What is the cheapest endpoint that can do this task well enough?"*

### Why DISCARD
- **Different problem.** Odysseus's cookbook optimizes *local VRAM placement across heterogeneous GPUs*. DQIII8's ladder optimizes *$/quality across remote APIs*. They are not substitutes.
- **DQIII8 has no fit-scoring problem to solve.** It's a single VPS with exactly one local model served by Ollama (tier C). There is no multi-GPU, no quant selection, no `n_cpu_moe` offload decision — `GPU_BANDWIDTH`, the quant ladder, and the offload math have **no input** in this environment. Importing `services/hwfit/` would add ~2000 lines of hardware-fit logic with nothing to act on.
- Cost, not VRAM, is DQIII8's binding constraint, and the existing ladder already encodes it.

**Verdict: DISCARD.** Revisit *only* if DQIII8 ever self-hosts multiple local GPU models and must choose quant/placement per card — at which point `profiles.compute_serve_profiles()` becomes a genuine reference. That condition is not on the roadmap.

## Summary

| Pattern | Verdict | One-line reason |
|---|---|---|
| 1. Scheduled tasks (`task_scheduler.py`) | **DISCARD** | daemon + queue + 4 DB tables to replace `cron` + `autonomous_loop.sh`; no measured need. Only `compute_next_run()` is worth remembering. |
| 2. fastembed ONNX vector+keyword memory | **DISCARD** | Odysseus memory is vector-only ChromaDB; DQIII8 already has vector + FTS5 + graph + RRF on sqlite-vec/bge-m3 (1024-d). fastembed's 384-d ONNX can't match the store. Only the `_http_embed_down` latch is a possible future micro-fix. |
| 3. VRAM-aware cookbook (`services/hwfit/`) | **DISCARD** | Solves local multi-GPU quant/placement; DQIII8's ladder solves cost-first API routing on a single-Ollama VPS. Different problem, no inputs here. |

**Net: 0 INTEGRATE, 0 ADAPT, 3 DISCARD.** Odysseus is a well-engineered local-first workspace, but every flagged pattern either duplicates a capability DQIII8 already implements more completely (memory), or solves a problem DQIII8's architecture (VPS, remote-API-first, single local model) does not have (scheduling daemon, VRAM fit-scoring). Two ideas are filed as contingent micro-notes — `compute_next_run()` and the `_http_embed_down` latch — neither justifying action today. The wu-wei call is to take nothing.
